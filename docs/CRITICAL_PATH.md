# 关键路径：从黑箱导出器到有状态商家系统

**中文** | [English](CRITICAL_PATH.en.md)

这份文档只保留项目中**真正改变下一步方向**的路径，不按“做了多少功能”记流水账。

## 阶段 0 — 先回答：这个软件到底是什么？

项目输入是一份第三方 Windows 包 `微店商品导出器-v1.2.0-客户版`，包含 EXE、`engine.dat`、`launcher.dat`、Node runtime、Playwright/ExcelJS 依赖和 Excel 模板。

采取静态优先、保护原包的方法：

```text
文件普查
→ SHA256 固化
→ EXE 架构
→ DAT 容器
→ 加载链
→ runtime 恢复
→ Playwright / API
→ Excel
→ 动态验证
```

关键结果：

- EXE 是小型 .NET Framework C# launcher，而不是核心业务程序；
- 受保护 DAT 被恢复成可读 PowerShell / ESM JavaScript；
- engine 从压缩 runtime 继续做到函数级解释；
- 最终建立字段级 lineage：微店 JSON 字段如何进入商城 Excel 列。

没有这一步，任何“从零重写”都只是复制表面功能，无法知道遗留系统已经解决过哪些真实边界。

## 阶段 1 — 静态推断到边界以后，建立运行时探针

继续做只读 runtime capture：

```text
真实商品列表 response
真实 SKU response
真实详情 response
页面实际分类行为
→ contract check
→ shape snapshot / baseline diff
```

探针确认列表/SKU/详情链和价格/库存血缘，并定位“分类读取 0 件”不是分类 API 本身错误，而是首页没有再触发原作者等待的 category seed 请求。

形成原则：**不知道外部系统真实行为时，打最小只读探针，不靠猜。**

## 阶段 2 — 用真实商城导入建立黄金契约

目标商城没有可见源码和正式 API 契约，因此使用黑盒验证：

```text
生成 Excel
→ 商城导入
→ 看真实成功/失败
→ 反推最小稳定契约
```

最终锁定 31 列、真实商品从第 2 行开始、分类留空、状态 `放置仓库` 等规则。

这一步把“抓到了数据”推进为“数据真的能进入业务系统”。

## 阶段 3 — 在契约稳定后再做基础操作能力

逐步增加：

- 指定分类；
- 全店关键词；
- 分类 + 关键词；
- 指定商品 ID / 链接；
- 全店最新；
- 分类最新。

多关键词还从错误的 AND 修成 OR，因为商家输入“兰蔻、雅诗兰黛”通常表示任意一个命中，而不是一个标题必须同时包含两个品牌。

## 阶段 4 — “最新”不能靠列表顺序猜，必须找真实时间证据

早期把接口倒序前 N 件近似成最新。重新检查真实 API 后发现 `addTime`，而且接口顺序与 `addTime` 并不严格一致。

因此建立：

```text
轻量列表：itemId + itemName + addTime
→ 按 addTime 排序
→ 只深抓目标商品的详情 / SKU / 图片
```

这成为后来“轻量索引 → 昂贵深抓”架构的来源。

## 阶段 5 — 纠正历史数量口径，重建全量历史基线

历史后台显示 5,000+ 导入记录，但商城当前约 1,600 商品。没有直接下结论“丢了三千多件”，而是解析全部历史 Excel：

```text
5,278 SKU/data rows
→ 约 1,628 个商品组

8 批历史
→ 1,729 raw groups
→ 1,721 个商品实体
```

问题从“商城是不是丢了几千商品”变成了“SKU 行数与商品数统计口径不同”。

更重要的是，这一步第一次恢复出**覆盖过去业务的完整历史商品身份**，让后续去重不再只记“新工具出现以后导过什么”。

## 阶段 6 — 从字符串去重升级成商品实体判断

用户明确指出：真正会随着商品数量爆炸的是人工筛重，不是本地 CPU 比较。只要激进索引不能保证不漏，就宁可程序多比一会儿。

因此当前规模下接受：

```text
100 × 1700 = 17 万次比较
200 × 5000 = 100 万次比较
```

五类证据最终形成：

1. 精确 itemId / skuId / 商品编码；
2. 容量、重量、数量、尺寸、色号、型号等硬规格；
3. 标题标准化；
4. 字符级模糊与换序容错；
5. Chrome Canvas + 64-bit dHash。

输出三态：

```text
DUPLICATE_CONFIRMED
NEW_CONFIRMED
REVIEW_REQUIRED
```

## 阶段 7 — 图片 URL 不可靠，所以进一步比较像素结构

先利用历史 Excel 的主图 URL 做归一化；但很快意识到不同 CDN、分辨率和 JPEG/WebP 重编码可能改变 URL 与文件字节，而画面仍然相同。

因此复用浏览器：

```text
URL
→ Chrome 解码
→ Canvas 9×8 灰度图
→ 64-bit dHash
→ Hamming distance
→ 缓存
```

硬规格证据优先级更高，因此同图不同规格不会被误杀。

## 阶段 8 — 明知可以上 NLP，但主动克制

认真讨论过 tokenizer、自定义词典、embedding、向量数据库和更重的视觉模型。用户持续追问“是不是过度工程化”“能用就行”。

最终保持：硬规格正则、少量别名、标题归一化、字符 n-gram / bag / edit distance、dHash 和人工 Review。

原则：**允许最后少量不确定案例交给人，不为了消灭所有人工再造一套商品 NLP 系统。**

## 阶段 9 — 真正增量：N 个候选不是 N 个新品

如果最新 100 个候选里 80 个已存在，商家真正需要的是继续向后找满 100 个新品。

于是改成目标循环：

```text
按时间拿候选
→ 深抓一个
→ 去重
→ NEW 才 +1
→ 满 N 立即停止
```

## 阶段 10 — 模糊搜索、意图确认、深抓、去重分层

真实需求往往是一批模糊目标，而不是精确关键词：

```text
多个目标描述
→ 每个目标独立模糊排序
→ 展示候选列表
→ 人工选编号
→ 只抓选中商品详情/SKU
→ 五层历史去重
```

搜索负责高召回，人负责最终确认意图，去重负责高精度身份判断。

## 阶段 11 — 先判断“大概是什么商品”，再决定去哪搜

v2.2 模糊搜索仍可能扫全店 2,000+ 商品。v2.3 增加一个薄的商品类型路由层，不做 `Tommy → 衣服` 这类品牌硬编码，而是用“卫衣、短裤、牛仔、人字拖、面霜”等高信息量词段，与当前店铺真实分类评分：

```text
高置信 → 最佳分类
中置信 → 前 1～2 个分类
低置信 → 全店兜底
```

真实五个服饰目标全部路由到 `衣服鞋帽`，搜索面降到约 660～680，而且多个目标共享一次分类扫描。

## 阶段 12 — 建立请求预算，不和限流硬刚

全店扫描和激进重试出现 socket hang up / HTTP2 错误。正确方向不是继续堆 retry，而是：分类最新、有限智能窗口、渐进冷却、连续失败主动停止，以及分类路由优先缩小搜索空间。

## 阶段 13 — “兄弟版本继承历史”只是迁移补丁，不是长期架构

v2.3/v2.4 为升级兼容会扫描附近旧版本目录、找最大/最新 JSON 历史。用户直接指出：删掉 v1.8/v2.0/v2.3 也应该正常。

v2.5 因此拆成：

```text
GitHub = 代码/版本历史
Release ZIP = 可删除运行快照
SQLite = 持久业务状态
```

数据库固定在版本目录外，后续版本直接打开同一份状态。

## 阶段 14 — 状态存在还不够，还要能证明连续并恢复

接下来继续追问：如果 SQLite 本身断档或回滚怎么办？

v2.6 加入：

- SQLite `quick_check` / 外键检查；
- 内部商品历史高水位；
- 数据库外健康锚点；
- `runs` 运行账本；
- `export_batches` 导出账本；
- `PREPARED → MALL_IMPORTED`；
- daily / checkpoint backup；
- 显式恢复。

项目最终的问题不再只是“程序跑没跑”，而是：**商家的历史状态是否连续、可解释、可恢复。**
