# Decision Trace from Dialogue

> 这份文档专门保存**讨论中的转折**：最初方案是什么、用户哪里不同意、最终为什么改。对于求职展示，这比单纯 changelog 更能说明产品判断和工程取舍。

## T01 — “不要为了程序省时间，让人工承担复杂度”

### 初始方向

曾考虑通过商品指纹/索引先缩小历史候选，减少全量比较。

### 用户纠正

用户指出真正会爆炸的是**人工识别重复**，而不是机器几十万次比较：如果算法不能证明既不重复也不遗漏，就宁可程序多比一会儿，不要为了效率牺牲稳定。

### 最终设计

- 完整候选抓取；
- 与完整历史商品库充分比较；
- 约 `100 × 1700 = 170k`、`200 × 5000 = 1M` 次比较被视为可接受；
- 不用激进 ANN/指纹前置裁剪决定新品。

### 求职信号

**优化的是最贵资源——人的时间，而不是最便宜的 CPU。**

## T02 — “先把 5000+ 这个数字的口径搞清楚”

### 表面现象

历史导入 5,000+，商城当前约 1,600，看起来像丢了几千商品。

### 关键判断

不能把导入行数直接当商品数；同一 SPU 有多个 SKU，一件商品可能展开多行。

### 实际对账

- 7 份历史表：5,278 SKU/data rows；
- grouping 后约 1,628 product groups；
- 8 批进一步合并成 1,721 historical entities。

### 最终影响

这不是一次统计修正，而是为五层去重建立了**全量历史事实底座**，也免去了客户之后随着商品数增长不断人工筛重。

## T03 — “URL 相同可以说明问题，但 URL 不同不能说明图片不同”

### 初始证据

历史 Excel 本来就有主图 URL。标准化 CDN URL、去参数，同 URL 可以作为强证据。

### 用户关注

不同来源/CDN 可能给同一张图完全不同的 URL；如果只比较 URL 会漏判。

### 最终设计

复用 Playwright / Chrome 读取真实像素，Canvas 9×8 → 64-bit dHash → Hamming distance，并缓存结果。

### 证据层级

- URL 相同：强证据；
- URL 不同但 dHash 近：独立视觉证据；
- 硬规格冲突：直接否决“同商品”，即使 dHash=0。

### 工程取舍

没有额外引入 OpenCV、TensorFlow、GPU 或视觉模型。

## T04 — “Tokenizer 能做，但会不会过度工程化？”

### 初始可选方案

讨论过：

- 中文 tokenizer；
- 自定义商品词典；
- embedding / vector DB；
- 多语言语义匹配；
- 更复杂视觉感知。

### 用户追问

重点不是“能不能加”，而是“加了以后是不是为了技术而技术”；业务允许少量人工二次筛选，工具首先要务实、稳定、双击可用。

### 最终设计

不加 tokenizer / embedding：

```text
regex hard specs
+ compact aliases
+ text normalization
+ char 2/3-grams
+ char bag
+ edit distance
+ dHash
+ REVIEW_REQUIRED
```

### 原则

**允许最后 10% 给人看，不为了消灭所有人工而造一套商品 NLP 系统。**

## T05 — “搜索和去重不能混成一个算法”

### 需求

一次输入多个模糊目标，例如：

- 32度女士抓绒外套；
- CK 女款人字拖；
- Hollister 女士浅灰色卫衣；
- Costco 清仓女士牛仔短裤。

### 最终分层

```text
多目标 fuzzy ranking
→ 每个目标展示列表
→ 人工编号选择
→ 只抓所选商品
→ full detail / SKU
→ five-layer dedupe
```

### 为什么

搜索需要高召回；去重需要高精度。自动替用户选择 fuzzy top1 会把“相似”误当成“意图确认”。

## T06 — “先从词里看出大概是什么，再路由分类”

### 问题

v2.2 模糊搜索每次全店扫 2,000+，网络请求多，容易慢和断。

### 方案取舍

没有建立：

```text
Tommy → 衣服
CK → 鞋
Hollister → 衣服
```

这种品牌硬编码。

而是抽取高信息量商品类型词段：

```text
卫衣 / 牛仔 / 外套 / 短裤 / 女装
人字拖 / 凉鞋 / 运动鞋
面霜 / 精华 / 护肤
...
```

再和**当前店铺真实分类名称**评分。

### 置信度

- high → top category；
- medium → top 1–2；
- low → whole-shop fallback。

### 真实回放

5 个服饰目标全部路由 `衣服鞋帽`，搜索面从全店 2,000+ 降到约 660～680，而且多个目标共享一次分类扫描。

### 原则

路由只是 request reduction，不是商品身份判断。因此它可以简单、可解释、有 fallback。

## T07 — “最新”不能靠接口列表顺序猜

### 早期实现

接口 `sortOrder=desc`，直接取前 N 件。

### 重新审查

真实 API 存在 `addTime`，且接口顺序与 `addTime` 不严格一致。

### 最终设计

```text
cheap list fields: itemId / itemName / addTime
→ sort by addTime
→ select target
→ expensive detail/SKU/image only for selected
```

后续又根据网络风控把 full exact scan 调整为 category-first / bounded window 日常策略。

---

## T08 — “打探针，而不是继续猜外部系统”

### 例 1：微店 API

运行时 capture 抓真实 list/SKU/detail，验证字段血缘，并发现分类 seed 不再由首页触发。

### 例 2：商城当前存量

只读探针监听商城商品列表网络 JSON，用来和历史 Excel 对账，而不是靠后台显示数字猜商品丢失。

### 原则

**外部系统不可见时，最小只读实验 > 长篇推测。**

## T09 — “两个失败不等于 SKU 有隐藏上限”

### 表面相关

450 行导入中失败 2 行，而两个 SPU SKU 数异常高。

### 候选假设

“商城也许最多 30/50 SKU，超过就拆 SPU。”

### 用户要求

不能凭感觉设阈值，需要看真实失败数据和回归。

### 最终证据

错误是 `规格已存在`，两条最终规格字符串重复。

### 修复

同 SPU 内 canonical spec 去重/冲突报告，450 → 448，不拆 SPU。

### 原则

**相关性不升级为业务契约。**

---

## T10 — “最新 100”真正想要的是“100 个我没有的新品”

### 原实现

取最新 100 → 去重 → 剩多少导多少。

### 用户目标

如果 80 个已导入，不能只给 20 个新品；应该继续向后找。

### 最终设计

逐件深抓 + 去重，直到 `NEW_CONFIRMED == N` 或候选范围耗尽。

这是典型的从**实现单位**转成**业务结果**。

## T11 — “兄弟姐妹找历史”只是兼容补丁，不是架构

### 当时状态

新版本启动时会扫描附近旧版本目录，比较谁的历史更大/更新，然后继承。

### 用户直接质疑

> 每次读写还要找一遍周围有没有“兄弟姐妹”，太麻烦；如果把 v2.2、v2.0、v1.8 全删掉，它也应该不出错。

### 最终设计

v2.5：

```text
GitHub = source/version history
Release = disposable runtime
SQLite = persistent business state
```

所有历史商品、dHash、同店历史和事件进入版本目录外 `state.sqlite3`。

### 更进一步的纠错

第一版又把 `.git` 放进 v2.5 可删除目录。用户立刻发现矛盾：删 v2.5 不是把 Git 仓库也删了？于是进一步修成**远端 GitHub 独立、Release 无 `.git`、SQLite 独立**。

### 求职信号

这不是“用了 SQLite”，而是识别出了**三种不同生命周期**。

---

## T12 — “内部候选池不是用户需要理解的业务数量”

### 现象

用户目标只要 5 个新品，终端却显示 200 候选、148 深抓候选，容易误以为要抓 148～200 件。

### 实际行为

最终只深度核验约 15 件就找到 5 个新品并停止。

### 设计修正

UI 应只强调：

```text
目标 5
已核验 X
已找到 Y/5
```

内部轻量索引/候选池只在诊断日志需要，不应该作为主业务反馈。

### 原则

**不要把算法内部结构泄漏成用户心智负担。**

---

## T13 — “Excel 准备好”不等于“商城成功导入”

v2.6 将两个状态拆开：

```text
PREPARED
→ operator confirms mall accepted
→ MALL_IMPORTED
```

并用 `runs`、`export_batches`、checkpoint 和 health anchor 建立可观测状态。

# 这些决策共同形成的工作方式

1. **先找真实证据，再升级结论。**
2. **优化人工成本，不盲目优化机器成本。**
3. **高风险判断用保守规则；低风险路由可以用简单启发式。**
4. **搜索、身份判断、用户意图、业务结果分别建模。**
5. **允许 UNKNOWN / REVIEW，而不是强迫所有东西二元化。**
6. **能用轻量确定性算法解决，就不为了“AI 感”引入重依赖。**
7. **程序代码、运行包、业务历史必须有各自正确的生命周期。**
8. **内部算法状态不能污染用户界面。**
