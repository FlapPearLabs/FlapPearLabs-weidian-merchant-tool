# 对话中的关键决策轨迹

**中文** | [English](DECISION_TRACE_FROM_DIALOGUE.en.md)

这份文档专门保存讨论中的转折：**最初方案是什么 → 用户哪里不同意 → 最终为什么改 → 这个决定在求职展示里说明什么能力。**

## T01 — 不要为了机器省时间，把复杂度转嫁给人工

**最初方向：** 用商品指纹/索引先缩小历史候选，减少完整比较。

**用户纠正：** 真正会随着商品数爆炸的是人工识别重复，而不是机器几十万次比较。如果近似裁剪不能保证不漏，就宁可程序多算一会儿。

**最终设计：** 完整候选与完整相关历史充分比较；`100×1700=17万`、`200×5000=100万` 次商品级比较都可以接受。

**求职信号：** 优化最贵的资源——人的注意力，而不是最便宜的本地 CPU。

## T02 — 先把“5000+ 历史记录”的统计口径搞清楚

**表面现象：** 历史导入 5,000+，商城当前约 1,600，看起来像丢了几千商品。

**关键判断：** 导入行数不能直接当商品数，同一个 SPU 有多个 SKU，一件商品可以展开多行。

**实际对账：** 5,278 SKU/data rows → 约 1,628 个商品组；8 批再归并 → 1,721 个历史商品实体。

**最终影响：** 这不是一次简单统计修正，而是为五层去重建立了覆盖过去业务的全量历史事实底座。

## T03 — URL 相同可以说明问题，URL 不同不能说明图片不同

**初始证据：** 历史 Excel 已有主图 URL，去参数和 CDN URL 标准化后，同 URL 可以作为强证据。

**用户关注：** 不同来源/CDN 可能给同一张图完全不同的 URL，只比较 URL 会漏判。

**最终设计：** Playwright/Chrome 解码真实像素 → Canvas 9×8 → 64-bit dHash → Hamming distance → 缓存。

**证据层级：** URL 相同是强证据；URL 不同但 dHash 近是独立视觉证据；硬规格冲突可以直接否决“同商品”，即使 dHash=0。

## T04 — Tokenizer 能做，但会不会过度工程化？

**讨论过的方案：** 中文 tokenizer、自定义词典、embedding/vector DB、多语言语义匹配、更复杂视觉模型。

**用户追问：** 重点不是“能不能加”，而是“加了以后是不是为了技术而技术”；业务允许少量人工二次筛选，工具首先要务实、稳定、双击可用。

**最终设计：** 硬规格正则 + 少量别名 + 标题归一化 + 字符 2/3-gram + 字符 bag + 编辑距离 + dHash + `REVIEW_REQUIRED`。

**原则：** 不为了消灭最后少量人工，就额外造一整套商品 NLP 系统。

## T05 — 搜索和去重不能混成一个算法

**真实需求：** 一次输入多个模糊目标，分别看到最像的候选，人工选出真正想要的几件，然后只抓这些商品。

**最终分层：** 多目标 fuzzy ranking → 候选列表 → 人工选号 → 只深抓选中商品 → 五层历史去重。

**原因：** 搜索追求高召回，去重追求高精度；模糊 top1 只能说明“像”，不能替用户确认意图。

## T06 — 先从词段看出“大概是什么商品”，再路由分类

**问题：** v2.2 模糊搜索仍可能扫全店 2,000+ 商品。

**没有采用：** `Tommy → 衣服`、`CK → 鞋`、`Hollister → 衣服` 这种品牌硬编码。

**采用：** 从“卫衣、短裤、牛仔、人字拖、面霜”等高信息量商品类型词段，和当前店铺真实分类名称评分。

```text
高置信 → 最佳分类
中置信 → 前 1～2 个分类
低置信 → 全店兜底
```

真实五个服饰目标把搜索面从全店 2,000+ 降到约 660～680，而且多个目标共享一次分类扫描。

**原则：** 路由只是低风险的 request reduction，后面仍然有人工选号和五层去重。

## T07 — “最新”必须由 `addTime` 证明，不靠接口顺序猜

**早期实现：** 取接口列表最前面的 N 件。

**重新审查：** 真实 response 存在 `addTime`，而且列表顺序与它并不严格一致。

**最终设计：** 轻量 `itemId/itemName/addTime` 索引 → 按时间排序 → 只对目标商品抓详情/SKU/图片。

## T08 — 对外部系统打探针，不继续扩展推测

典型两次：

- 微店 runtime capture 验证 list/SKU/detail，并定位 category seed 行为变化；
- 商城只读探针 + 历史 Excel 对账，用来理解当前存量，而不是猜“几千商品去哪了”。

**原则：最小只读真实证据 > 长篇推测。**

## T09 — 两个失败不等于“商城有隐藏 SKU 上限”

**表面相关：** 450 行导入失败 2 行，恰好两个 SPU SKU 特别多。

**诱人方案：** 设置 30/50 SKU 阈值，超过就拆 SPU。

**用户要求：** 不能凭感觉设规则，要追真实失败数据。

**最终证据：** 错误是 `规格已存在`，两条最终规格字符串重复。

**修复：** 同 SPU 内 canonical spec 去重/冲突处理，450 → 448，不拆商品。

## T10 — “最新 100”真正想要的是“100 个我没有的新品”

**原实现：** 取最新 100 → 去重 → 剩多少导多少。

**用户目标：** 如果 80 个已导过，不能只给 20 个新品，应该继续向后找。

**最终设计：** 逐件深抓与去重，直到 `NEW_CONFIRMED == N` 或候选范围耗尽。

**求职信号：** 从实现单位切换到业务结果。

## T11 — “兄弟姐妹找历史”只是兼容补丁，不是架构

**当时状态：** 新版本启动时会扫描附近旧版本目录，比较谁的 JSON 历史更多/更新，然后继承。

**用户直接质疑：** 删除 v2.2、v2.0、v1.8 等旧版本后，系统也应该正常。

**最终设计：** GitHub=代码和版本历史；Release=可删除运行包；SQLite=持久业务状态。

**进一步纠正：** 第一版还一度把 `.git` 放进可删除 Release 目录，用户立即指出删 v2.5 不就把 Git 仓库也删了，于是进一步拆成远端 GitHub、无状态 Release、独立 SQLite。

## T12 — 200/148 是内部候选池，不应该成为用户心智

**现象：** 目标只要 5 个新品，终端却展示 200/148，看起来像要抓几百件；实际可能深度核验约 15 件就达到目标。

**最终设计：** 主界面展示目标 / 已核验 / 已找到；内部 pool 只进入诊断日志。

**原则：** 不把算法内部结构泄漏成用户的业务数量。

## T13 — Excel 准备好，不等于商城已经导入

v2.6 将状态拆成：

```text
PREPARED
→ 用户确认商城实际接受
→ MALL_IMPORTED
```

并用 `runs`、`export_batches`、checkpoint 和 health anchor 建立可观测状态。

---

## 这些决策共同形成的工作方式

1. 先找真实证据，再把观察升级成规则；
2. 优先优化人工成本，不盲目优化机器成本；
3. 高风险身份判断使用保守逻辑，低风险路由可以使用简单 heuristic；
4. 搜索、用户意图、商品身份和业务成功分别建模；
5. 允许 UNKNOWN / REVIEW，不强迫所有情况二元化；
6. 轻量确定性算法够用时，不为了“AI 感”引入重依赖；
7. 源码、Release、业务历史必须拥有不同的正确生命周期；
8. 算法内部状态不应该污染使用者的主界面和心智模型。
